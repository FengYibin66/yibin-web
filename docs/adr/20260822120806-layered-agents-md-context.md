# 20260822120806. AGENTS.md 分层上下文：就近加载，且必须标注「现状 ≠ 目标」

- 状态：已接受
- 索引：每个有约定的目录放一份 AGENTS.md，操作该目录前先读；根目录不放 AGENTS.md 以 CLAUDE.md 为准；临时实现必须显式标注不可作为目标架构反推依据
- 日期：2026-08-22

## 背景

本仓库此前的 AI 协作上下文实际为零。全仓只有两份相关文件，且都不是项目内容：

- `apps/resume/AGENTS.md` — 5 行，是 Next.js 自动注入的样板（`<!-- BEGIN:nextjs-agent-rules -->`）
- `apps/resume/CLAUDE.md` — 1 行，内容是 `@AGENTS.md`
- 根目录**没有** `CLAUDE.md`

后果是每次 agent 会话都要从零摸索：跑什么命令、目录职责是什么、哪些是故意的取舍、哪些是待修的缺陷。而它摸索的依据只有代码——代码无法表达"这里是临时方案"或"这个空目录是废弃的"。

本仓库有两处正在产生实际误导：

- `packages/` 是空目录，但 `pnpm-workspace.yaml` 里没有它——看目录树会以为有共享层
- `apps/resume/features/lab/` 下有 8 个**全空**子目录（experience / context / loading / corridor / hooks / shaders / dom），同时 `components/lab/` 和 `lib/lab/` 才是真正的实现位置。agent 看到 `features/` 骨架会以为该往那里加代码

## 选项

- **A. 单一根 CLAUDE.md 承载全部约定**：一处维护；但个人项目也会到数千行，每次会话全量进上下文，且大部分与当前任务无关。
- **B. 分层 AGENTS.md，就近加载**：agent 只读它真正要动的目录那一份。代价是文件数增加、需要同步纪律。
- **C. 不写文档，靠代码自解释**：零维护；但代码只能表达"是什么"，无法表达"为什么"和"这是临时的"。上述两处死结构正是 C 的必然产物。

## 决策

选 **B**，并附三条纪律：

1. **就近读取**：操作任一目录下的文件前，先读该目录的 `AGENTS.md`；没有则向上找最近的一份。
2. **根目录不放 `AGENTS.md`**，以 `CLAUDE.md` 为准。两份同级文档会成为两个事实来源，冲突时无法裁决。
3. **内容与目录同步是硬要求**：目录职责变化必须在同一次改动里更新 `AGENTS.md`；新建有约定的目录同步补建。

**并额外要求一条 EpicGlobal 的做法**：临时实现必须在 `AGENTS.md` 顶部显式声明「当前实现不是目标架构」，且写明**哪些缺失是已知取舍、不是待修缺陷**。

这条的必要性在本仓库已经可以验证：`apps/portal/` 没有测试（0 个）、没有契约、类型手写。若不标注，agent 面对它只有两种同样错误的反应——把这套模式当范例扩散到别处，或者热心地开始"补齐"从而扩大改动面。标注之后它才能知道：这是已知负债，有对应 ADR，不要就地发挥。

## 影响

- 正面：单次会话上下文成本随任务范围收敛而非随仓库规模膨胀；「已知取舍 vs 待修缺陷」可被区分；死结构被显式识别（本 ADR 已发现两处）。
- 负面：新增约十份文档的维护义务；不同步的 `AGENTS.md` 比没有更糟——它会让人和 AI 停止怀疑。缓解手段是把它写进 CLAUDE.md 硬约束，并在 review 时检查。
- 影响面：新增 `apps/`、`apps/portal/`、`apps/resume/`（覆盖样板）、`apps/auto-wechat/`、`docs/`、`docs/adr/`、`scripts/`、`docker/`、`config/` 的 `AGENTS.md`；删除 `packages/` 与 `apps/resume/features/` 死结构。
