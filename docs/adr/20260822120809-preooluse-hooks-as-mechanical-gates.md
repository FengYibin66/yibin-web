# 20260822120809. 用 PreToolUse hooks 做机制门禁，且必须 fail-closed

- 状态：已接受
- 索引：AI 红线用 `.claude/hooks/` 的 PreToolUse 脚本机制拦截而非文档请求；拦截须 `exit 2`，守卫自身异常必须映射为拦截；每条 hook 明确声明覆盖边界，不制造虚假安全感
- 日期：2026-08-22

## 背景

本仓库的 `.claude/` 只有 `settings.local.json`，**没有任何 hook**。所有对 AI 的约束（如果有过）都是文档里的请求。

文档请求与机制拦截的差别不是程度而是性质：文档要求 AI 在**它自己判断相关时**遵守，而 AI 判断相关性会失败——尤其在长会话、上下文被压缩、或它正专注于另一个目标时。已经在本仓库留下痕迹的例子：9 个残留 `worktree-agent-*` 目录和 16 条分支，说明没有任何机制在收尾时清理或阻止扩散。

需要机制拦截的红线（按本仓库实际风险排序）：

1. **直接 push main** —— main 是部署源（ADR 20260822120807 改为人工触发后风险下降，但 main 仍是唯一发布分支）
2. **`git --no-verify`** —— 绕过本地检查
3. **硬编码 secret** —— 本仓库有 `.env.production`、`.env.shared.local`，且部署脚本处理证书与数据库密码
4. **手改生成/派生产物** —— ADR 20260822120808 引入派生类型后，手改派生出口会重新制造漂移

## 选项

- **A. 只写文档约定**：零成本；但对 AI 不可靠（见上）。
- **B. 只靠 git hooks（pre-commit）**：能拦提交时刻；但 agent 在提交前已经把文件改了，且 `--no-verify` 可绕过。
- **C. PreToolUse hooks 在工具调用前拦截**：在改动发生**之前**拦下，agent 立刻收到拒绝原因并可自行改道。
- **D. B + C 双层**：本地防线最全；但对个人项目，两套规则需保持同步，维护成本翻倍。

## 决策

选 **C**，并附两条设计约束：

**1. Fail-closed：守卫跑不起来必须等于拦截。**

Claude Code 的 PreToolUse 只把 `exit 2` 当作拦截，其余非零退出码按放行处理。这意味着一个 `#!/usr/bin/env python3` 的守卫在 python3 缺失时退出码是 127 —— **「守卫坏了」会静默变成「放行」**。因此凡逻辑不在纯 bash 内的守卫，都用薄 shell 包装，包装唯一的职责是把任何异常映射成 `exit 2`。包装里不含任何路径或匹配逻辑。

**2. 每条 hook 必须声明自己不覆盖什么。**

例如「禁止手改派生产物」挂在 Edit / Write 上，那么 `sed -i`、`>`、`rm` 走的是 Bash，本侧一概不管。**正确做法是把这条边界写进 `.claude/hooks/AGENTS.md`，而不是试图解析 Bash 命令**——Bash 的改写形态漏不完（`python -c`、`perl -i`、`awk > tmp && mv` …），挡住三五种只会制造虚假安全感，比明说「本侧不管、CI 才是防线」更危险。

**3. Hook 自身要有回归测试。** 门禁脚本是生产代码：它静默失效时没有任何症状，只有下一次事故。

## 影响

- 正面：红线从"希望 AI 遵守"变成"AI 无法违反"；违规时 agent 得到明确原因并自行改道，不需要人在旁边看着。
- 负面：误拦会打断正常工作流（缓解：拦截信息必须写清放行方式）；hooks 只在本机 Claude Code 生效，不是 CI 替代品——**CI 才是最终防线**，hooks 只是把反馈提前。
- 影响面：新增 `.claude/hooks/`（脚本 + `AGENTS.md` + `tests/`）、`.claude/settings.json` 注册。注意 `settings.json` 需提交入库（区别于 `settings.local.json` 的本机配置）。
