# 20260903211320. 源码门禁改用 TypeScript AST 扫描，不用正则；产物指纹同时覆盖输出

- 状态：已接受
- 索引：resume 的三条源码门禁（相机所有权、Lab 漏译、覆盖层对比度）从「grep + 手写字符串剥离器」改为共用一个基于 `typescript` 编译器 API 的扫描器（`__tests__/helpers/sourceScan.ts`）；变异测试证明正则版对 20 个变异漏掉 10 个，其中包括仓库自己白名单里登记过的写法；素材指纹从「只算输入」改为「输入 + 输出」，让手改派生产物也能被 `--check` 抓到
- 日期：2026-09-03

## 背景

ADR 20260903140617 / 20260822120809 的共同做法是「把红线变成机制」，落地形态是几条 grep 门禁，并在 `apps/resume/AGENTS.md` 里写明「已是机制，不再是约定」。独立 review 对这些门禁做了 20 次真实变异（改实现，看哪条测试变红），**10 个变异存活，全部集中在这三条正则门禁上**：

相机所有权门禁（`__tests__/cameraOwnership.test.ts`）：

- `camera.position.setZ(5)`、`camera.rotation.set(0,1,0)`、`camera.rotateX(0.1)`、`camera.position.applyMatrix4(m)`、`gsap.to(camera.rotation, …)` 全部不在 `WRITE_PATTERNS` 里。其中 `camera.rotation.set` 尤其难堪：`DoorSection.tsx` 正在用这种写法，白名单注释里也登记过它是「四处违例之一」——**门禁连自己登记过的形态都不认**，把它搬到新文件不会红。
- `const cam = camera; cam.position.set(...)` 绕过（正则锚定 `camera.` 字面）。
- 手写的 `stripCommentsAndStrings` 把 JSX 文本里的撇号当成字符串起点：一个 `Don't touch` 就能吞掉同文件后面整段代码直到下一个引号，让其中所有写点隐身。同样的问题在正则字面量（`/['"]/`、`/https?:\/\//`）上重现。

漏译门禁（`__tests__/labI18n.test.ts`）：模板字符串与跨行 JSX 文本抓不到（prettier 一折行就漏，而这是最常见形态）；字符串里的 URL 含 `//`，被当成行注释起点，吞掉同行后面的硬编码。

对比度门禁（`__tests__/labContrast.test.ts`）：只匹配 `rgba(...)`，`#hex`、`rgb()`、`opacity` 全不看。实测入口页桌面的 tagline 是 2.71、footer 1.67、ClassicPanel 的 eyebrow 1.61，同一段文案在手机侧已改到符合标准而桌面侧没有——门禁对此完全沉默。

另有一条相邻问题：`scripts/media/freshness.mjs` 的内容指纹只覆盖**输入**（源文件 + 生成脚本）。手改 `public/` 下的派生产物（追加一个字节）后 `--check` 依然全绿——CLAUDE.md 的「[机制] 不手改派生产物」这条红线对素材产物**没有机制**。

不决策会发生什么：这三条门禁被文档描述为机制，实际防护范围是「照抄注释里那几种写法的人」。它们不防换一个 API 名的人，更不防 prettier。而一旦有人相信它们是机制，就不会再在 review 里看这些点——虚假安全感比没有门禁更糟，这正是 ADR 20260822120809 自己写下的判定（「每条 hook 明确声明覆盖边界，不制造虚假安全感」）。

## 选项

- **A. 继续加正则。** 把漏掉的 5 类写法补进 `WRITE_PATTERNS`，剥离器再打几个补丁。优点：改动局部，半小时能做完。缺点：与「下一个 API 名」和「下一次 prettier 折行」赛跑，而这场比赛已经输过一次（写法清单在注释里都列过了，门禁仍然不认）。剥离器的本质问题是它在用正则做词法分析，补丁只能让它错得更晚。
- **B. 用 `typescript` 编译器 API 做一个共用扫描器。** 依赖已在（仓库本身是 TS）。提供三个查询：`cameraWrites`（找 `PropertyAccessExpression` 的赋值与方法调用，receiver 解析到 camera 或其一层别名，方法名取 three 的全部写方法集合）、`userStrings`（全部字符串 / 模板 / JSX 文本节点，天然免疫撇号、URL、折行）、`colorLiterals`（字符串节点里的 hex / rgb / rgba / hsl）。三条门禁共用。优点：词法与语法由编译器负责，撇号与 URL 类的假阴性按构造消失；一次投入三处受益；开发者可见文案（`new Error(...)`、`console.*` 实参）可以用**语法位置**精确豁免，而不是放宽匹配。缺点：扫描器本身有复杂度（需要自己的测试）；AST 遍历比 grep 慢（实测三条门禁合计增加约 1.5 秒，可接受）。
- **C. 换成 ESLint 自定义规则。** 优点：这是这类检查的标准形态，编辑器内即时反馈。缺点：**本仓库的 lint 从未跑通过**（根 CLAUDE.md「已知负债」明确记录：portal 缺依赖与配置、resume 的 `eslint-config-next` 版本与 flat config 不匹配），修它是一次独立的依赖升级决策、需要单独的 ADR。把门禁挂在一个跑不起来的工具上等于删掉门禁。等 lint 修好后可以再评估迁移。

## 决策

选 **B**。C 记录为「等 lint 负债偿还后重新评估」。

**判定原则：用正则判断代码结构，只能得到一个「大概率对」的门禁；而门禁的价值恰恰全部来自它不漏。** 凡是需要理解语法结构才能判定的规则（谁写了这个对象、哪些字符串会被用户看到），就用语法分析器，不用文本匹配。判断这类门禁是否够用的标准不是「现在是绿的」，而是「构造 N 个绕过形态，有几个能活下来」。

同时把两条相关的门禁缺陷一并修掉（形态唯一，不构成决策）：

- 相机门禁的白名单从**文件级**改为**写点计数棘轮**（`{ 文件: 期望写点数 }`）：文件级白名单的漏洞是「已在名单里的文件再加 20 个写点也是绿的」。
- 素材指纹加入输出摘要，`--check` 同时比对输入与输出。
- `__tests__/galleryDoor.test.ts` 的「衬底画在最前面」是空断言（只检查衬底存在、后面有元素，从不检查它**前面**有没有元素），补齐。

**验收标准写进测试：** review 用过的 20 个变异全部复现为一份变异清单，要求 20/20 被杀。

## 影响

- 正面：三条门禁的假阴性按构造消失；新增门禁可以复用扫描器而不必再手写剥离器；手改素材产物有了机制；门禁的防护力第一次有了可量化的验收标准（变异存活数）。
- 负面：扫描器是新的关键基础设施，它自己静默失效时同样没有症状——必须有回归测试（与 CLAUDE.md 对门禁脚本的要求一致）；测试时间增加约 1.5 秒；别名追踪只做一层，`const a = camera; const b = a; b.position.set()` 仍会漏（记录为已知边界，两层以上的间接在真实代码里没有出现过）。
- 影响面：新增 `apps/resume/__tests__/helpers/sourceScan.ts` 与其测试；改写 `__tests__/{cameraOwnership,labI18n,labContrast,galleryDoor}.test.ts`；`scripts/media/freshness.mjs` 与四条流水线的 `--check`。
